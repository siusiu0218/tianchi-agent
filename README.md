## 1. 项目定位

“共情副驾”是一套服务于人工客服的 AI 辅助系统。它融合聊天记录、订单和工单数据，帮助客服快速理解消费者问题、识别情绪与服务风险、生成有事实依据的共情回复，并持续跟踪问题是否闭环。

让 AI 成为客服的决策副驾：

- 帮助客服快速看懂消费者正在经历什么；
- 从订单和工单中找到回复依据；
- 对不良反应、情绪升级和未闭环问题及时预警；
- 给出可编辑、可追溯、需要人工确认的处理建议；
- 把风险从发现、分派、处理一直跟踪到闭环。

## 5. 核心用户与价值

### 5.1 一线客服

需要在较短时间内理解问题、核对订单、组织回复并判断是否升级。系统为其提供上下文摘要、风险提示、回复草稿和下一步操作建议。

### 5.2 客服主管

需要发现正在恶化的服务问题、合理分派任务并检查闭环。系统为其提供风险队列、趋势、负责人、处理状态和超时提醒。

### 5.3 风控或专业处理人员

需要接收不良反应、异常退货等高风险事件，并获得完整证据链。系统应保留原始聊天、订单事实、模型判断依据和人工处置记录。

## 6. 产品方案

### 6.1 智能接待辅助插件

插件位于客服工作台右侧，随当前会话变化自动刷新，建议展示：

- 消费者当前诉求；
- 业务场景与置信度；
- 情绪状态及变化趋势；
- 风险等级与触发依据；
- 关联订单摘要；
- 历史及当前工单；
- 尚未解决的问题；
- 推荐回复；
- 下一步处理动作；
- 人工确认、修改和反馈入口。

推荐回复使用“三段式”：

1. 共情：先回应消费者的感受；
2. 事实：引用真实订单、物流或工单状态；
3. 行动：说明下一步、负责人和预计处理方式。

### 6.2 风险异常预警看板

看板建议包含：

- 当前高风险会话数；
- 待处理不良反应事件；
- 情绪持续升级会话；
- 超时未闭环工单；
- 异常退货或风控案例；
- 风险等级和业务场景分布；
- 处理负责人及当前状态；
- 从发现到闭环的耗时；
- 会话、订单和工单统一时间线。

### 6.3 Agent 工作流

```text
接收当前会话
    ↓
解析消费者诉求与情绪
    ↓
查询订单、物流和历史工单
    ↓
规则引擎与大模型联合判断风险
    ↓
检索服务规则与安全边界
    ↓
生成回复草稿和下一步建议
    ↓
客服人工确认或修改
    ↓
创建工单草稿 / 更新跟进状态
    ↓
看板持续追踪直至闭环
```

建议的 Agent 工具：

- `get_conversation_context`
- `get_order_detail`
- `get_ticket_history`
- `assess_service_risk`
- `retrieve_service_policy`
- `draft_empathic_reply`
- `create_ticket_draft`
- `update_followup_status`

创建工单、退款、补偿、对消费者作出承诺等动作必须经过人工确认。

## 7. MVP 范围

第一版只完成两个黄金场景，不要一开始覆盖全部 41 个细分场景。

### 场景 A：不良反应高风险升级

演示流程：

1. 消费者描述红肿、刺痛或就医；
2. 系统识别为高风险并展示原文证据；
3. 查询关联订单、商品和不良反应工单；
4. 生成谨慎的共情回复，不作医学诊断；
5. 建议立即转交专业处理人员；
6. 客服确认后生成工单草稿；
7. 看板显示负责人、状态和闭环进度。

### 场景 B：物流或换货问题闭环

演示流程：

1. 消费者反馈物流停滞、破损或少件；
2. 系统自动关联订单和物流/换货工单；
3. 展示原物流和补发物流，避免混淆；
4. 生成包含准确事实和下一步的回复；
5. 客服确认处理方案；
6. 看板跟踪至工单完成。

### 暂不进入 MVP

- 模型微调；
- 全自动退款或赔付；
- 复杂多智能体角色表演；
- 没有原图情况下的图像识别结果展示；
- 对全部业务场景同时做高保真支持；
- 基于 MOCK 数据推算真实商业收益。

## 9. 关键数据模型

最小核心实体：

- `Conversation`：会话 ID、买家、起止时间、当前场景；
- `Message`：消息 ID、序号、角色、时间、文本、内容类型；
- `Order`：订单号、商品、金额、状态、物流；
- `Ticket`：工单号、类型、状态、负责人、创建和完成时间；
- `RiskAssessment`：风险等级、类型、依据、置信度、模型版本；
- `ReplySuggestion`：共情段、事实段、行动段、引用依据；
- `FollowUp`：负责人、状态、截止时间、闭环记录；
- `HumanFeedback`：采纳、修改、驳回及原因。

所有模型生成结论都应保存来源消息和业务字段引用，避免只保存一段无法审计的自然语言。

## 10. 风险分级建议

| 等级 | 示例 | 系统行为 |
| --- | --- | --- |
| P0 紧急 | 明确就医、严重不适或其他重大安全信号 | 强提醒、禁止自动承诺、立即转人工专业处理 |
| P1 高 | 情绪明显升级、异常退货、高价值订单重大问题 | 进入主管队列并设置处理时限 |
| P2 中 | 工单未闭环、多次催促、普通物流异常 | 提醒客服并跟踪状态 |
| P3 低 | 常规咨询和一般服务请求 | 提供回复和操作建议 |

风险引擎采用“确定性规则兜底 + LLM 补充理解”：

- 明确安全关键词和状态规则由程序直接判断；
- LLM 用于理解语境、解释依据和生成回复；
- 低置信度或规则冲突时交给人工；
- 不允许模型自行降低规则触发的高风险等级。

## 11. 大模型输出约束

模型应返回结构化 JSON，而不是只有一段回复：

```json
{
  "scene": "不良反应",
  "intent": "咨询面部红肿刺痛处理",
  "emotion": "焦虑",
  "risk_level": "P0",
  "risk_reasons": ["消费者提到红肿刺痛", "消费者自述已就医"],
  "evidence_message_ids": ["..."],
  "unresolved_items": ["需要专业人员回访"],
  "reply": {
    "empathy": "...",
    "facts": "...",
    "action": "..."
  },
  "recommended_action": "创建不良反应工单草稿并转专业处理",
  "requires_human_confirmation": true
}
```

基本约束：

- 订单、物流和工单事实只能来自工具查询结果；
- 没有数据时明确写“暂未查询到”，不能编造；
- 不提供医学诊断；
- 不擅自承诺退款、赔付、时效或处理结果；
- 回复建议始终可编辑；
- 保存模型版本、提示词版本和输入依据。

## 12. 评测方案

### 12.1 场景识别

使用聊天文本预测业务场景，以数据中的 `scene_major` 和 `scene_minor` 作为评测标签。

注意：这两个字段只能用于离线评测，不能同时作为模型输入，否则会造成标签泄漏。数据划分应按会话或买家分组，不能按消息随机拆分。

建议指标：

- 一级场景 Macro-F1；
- 二级场景 Macro-F1；
- 高风险场景召回率；
- 混淆矩阵。

### 12.2 风险识别

优先评估：

- 不良反应是否漏报；
- 已就医案例是否全部进入最高优先级；
- 异常退货是否正确进入风险队列；
- 未闭环工单是否被发现；
- 风险依据能否定位到原始消息或字段。

风险任务中应优先保证高风险召回，再控制误报。

### 12.3 回复质量

人工盲评 60–100 个会话案例，评分维度：

- 共情自然度；
- 事实准确性；
- 问题覆盖完整性；
- 下一步可执行性；
- 是否存在编造；
- 是否越权承诺；
- 不良反应场景是否遵守安全边界。

### 12.4 工作流效率

可在模拟环境测量：

- 完成一次问题定位所需步骤；
- 生成建议的延迟；
- 订单/工单字段引用正确率；
- 工单类型建议准确率；
- 客服采纳、修改和驳回比例。

只能称为“模拟任务结果”，不能外推成真实业务收益。

## 14. 演示脚本

推荐主 Demo 使用不良反应场景：

1. 打开一条消费者反馈红肿刺痛的会话；
2. 插件自动显示 P0 风险及对应原文；
3. 展开订单、商品和历史工单；
4. 展示三段式共情回复；
5. 展示系统没有作医学诊断，也没有擅自承诺；
6. 客服修改并确认；
7. 创建不良反应工单草稿；
8. 主管看板出现新的高风险任务；
9. 更新负责人和状态；
10. 完成后在时间线中形成闭环记录。

备用 Demo 使用物流或换货场景，防止主场景演示失败。

## 15. PPT 建议结构

官网未规定 PPT 页数。项目内部建议在官方模板基础上扩展为约 9 页：

1. 封面：作品名称、赛道和队伍；
2. 问题：客服为什么“看得见订单，却听不见情绪”；
3. 方案：插件 + 看板的服务闭环；
4. 使用场景：不良反应端到端案例；
5. 产品界面：风险、证据、回复和操作；
6. Agent 与数据架构；
7. 评测结果和安全机制；
8. 商业价值、限制和未来完善；
9. 结束页。

路演重点应放在一个完整故事，而不是堆叠模型名称或智能体数量。

## 16. 合规与安全

- 原始比赛数据只用于比赛；
- 外部服务按项目决策允许使用，但只发送完成当前任务所需的最少字段，并保留服务商、模型版本、发送字段和数据流向记录；
- 环境变量和密钥不得写入仓库；
- 日志中避免保存不必要的账号、地址等信息；
- 明确说明数据是 MOCK 数据；
- 使用免费可商用或已获得授权的字体和素材；
- 不良反应回复不作诊断、不推荐治疗、不淡化风险；
- 高风险结论保留人工审核和审计记录；
- 比赛结束后按主办方要求删除或停止使用数据。

## 17. 常见失败方式

- 只有聊天机器人，没有订单和工单证据；
- 只有大屏图表，没有可执行的闭环动作；
- 用已有场景标签冒充模型识别能力；
- 大模型生成不存在的物流、退款或处理时效；
- 展示很多 Agent 名称，但没有真实工具调用；
- 使用 MOCK 数据宣称真实投诉率下降；
- 缺少人工确认，允许模型直接退款或承诺；
- 在图片文件缺失时声称完成了真实多模态验证；
- 为覆盖大量场景牺牲两个核心场景的完成度；
- PPT 讲技术很多，却没有连续可用的产品 Demo。

## 18. MVP 完成标准

只有同时满足以下条件，才认为 MVP 完成：

- 能加载并展示真实比赛数据；
- 会话、订单和工单可以正确关联；
- 至少两个黄金场景端到端可运行；
- 风险结论显示原文或业务字段依据；
- 推荐回复引用的事实准确；
- 不良反应场景遵守安全边界；
- 创建工单等动作需要人工确认；
- 看板能反映任务状态变化；
- 有固定评测案例和可复现结果；
- 有备用演示路径；
- PPT、视频和代码口径一致。

## 19. 范围停止规则

如果下面任一项还不稳定，就不要继续增加场景、Agent 或视觉特效：

- 风险依据无法回到原始消息；
- 订单或工单事实可能被模型编造；
- 高风险事件可能漏报；
- 人工确认与状态闭环没有真正打通；
- 两个黄金场景不能连续完成演示；
- 评测结果无法复现。

先把“风险依据、订单事实、建议回复、下一步操作、闭环状态”五件事做扎实，再扩展其他能力。

## 20. 下一步行动

建议立即按以下顺序推进：

1. 运行只读数据画像与关联校验，冻结当前数据快照和可评价边界；
2. 保持现有原始文件原位只读，不覆盖、不改写；如后续建立 `data/raw/`，仅做带校验和的审计副本；
3. 根据数据画像建立评测集与标注口径；
4. 从现有数据中选定一个不良反应案例和一个物流/换货案例；
5. 先制作客服工作台和风险看板的静态界面；
6. 再接入规则引擎、模型和 Agent 工具；
7. 每完成一个功能，都用固定 Demo 案例回归验证。
