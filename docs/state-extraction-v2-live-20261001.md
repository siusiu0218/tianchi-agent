# 状态提取v2：分类拆分有效，任务自由文字仍需约束

日期：2026-10-01。用户同意继续后，将问题类型与当前待办、已提供信息、内部核实、客户补问拆开。新增 `scripts/evaluate_state_extraction_v2_live.py`；v1运行器增加可传入提示/校验器/开发预期的参数，默认仍是v1。原始v1输出不改写。

## 验证方式

新旧两轮发送的4个脱敏context逐项相等，改动是输出结构与提示；不提供人工目标标签。每时点1请求，无重试，模型仍为qwen3.8-max-0902，temperature=0、max_tokens=2600、enable_thinking=false。开发标签事前冻结于独立文件，不发给模型。

新增4项v2测试与原v1的4项合计8项通过，验证字段拆分、任务引文、缺失任务/旧结构拒绝、问题引用和执行状态边界。结构成功始终不允许自动回复。任务必要性、指代支持和是否遗漏仍须源文复核；程序没有通用语义判断能力。

## 4个时点的实际发现

| 时点 | 有效变化 | 仍需修订 |
| --- | --- | --- |
| S00001首次 | 识别泵头问题、初次报告，内部核对已关联订单，不再索要订单号 | 把系统通用的“无退款/打款/发货/转交凭证”扩展成当前全部核实事项，产生与初次破损阶段无关的任务 |
| S00001接受后 | 当前待办包含发新件与跟进旧件寄回；保留已发图片；先内部查看附件，不要求重交 | “发出全新粉底液”容易被当作执行指令。应表达为核对此前发新件安排及进度；执行仍为unknown |
| S00268首次 | 保留消费者报告与在医院的信息；内部核实和客户补问分开 | customer_questions为空，未覆盖本次设计要了解的发生时间/当前变化；又泛化出退款、发货等所有执行状态核实，缺少任务适用性判断 |

最终时点的“买家已提供门诊病历和医生诊断照片资料”引用仅有M3“资料给你”，具体资料类型还依赖M2指代；需要补充上下文引用。部分内部核实理由只引用系统无凭证说明，漏引具体历史客服承诺。引文存在和精确匹配不能验证这些语义关系。

issue_category、stage、execution三个开发枚举在4例均匹配事前预期，所有执行状态为unknown。但这只是这三个字段，不是整份提取准确率；任务/信息列表仍有上述错误和遗漏。也不能和v1混合focus的2/4作同口径准确率比较。

## 接下来先做离线修订

任务不要直接采用模型自由文字：候选任务用受控类型（核对换货、退款、报销、回访等）和原话引用表示，由程序生成“核实既有安排/进度”的展示文字。历史期限保留在历史承诺证据中，不能进入新指令；材料原件要求必须有独立政策依据。内部核实必须关联一个当前任务，不能从系统通用缺失提示扩展出全部业务动作。

将本轮“票据原件”“24小时回访”“初始阶段无关执行任务”“不适关键补问遗漏”保存为离线反例，先验证拦截与待人工处理路径，再决定新的接口实验。当前不自动追加API调用，也不把任务内容强行改成已通过。
