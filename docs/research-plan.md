## 1. 现状核对（已核过的关键事实）

数据是一个 Excel，8 张表：`数据说明 / 聊天记录 / 订单 / 补发换货工单 / 线下打款工单 / 物流工单 / 不良反应工单 / 售后退货工单`。

三个直接影响研究方案的发现：

1. **有金标签的只有「场景」**。`聊天记录` 表里有 `scene_major`（一级，10 类）和 `scene_minor`（二级，41 类），可当分类评测标签——但不能同时喂给模型（标签泄漏，README §12.1）。
2. **情绪、风险等级没有现成标签**。表里没有 `emotion` 列，也没有 `P0/P1/P2/P3` 列。这两个是产品核心卖点，**必须自己构造评测口径**，否则评测站不住。
3. **风险信号藏在工单字段里**，不用凭空造：`不良反应工单` 有「是否就医 / 是否停用 / 症状描述」，`售后退货工单` 有「是否异常 / 风控核实」，`补发换货工单` 有「客诉加急」。这些是把 P0/P1 落地的天然依据。

结论：第一优先级是**先把「什么能评、怎么评」定下来**，再谈模型。

## 2. 研究计划（分步：做什么 / 怎么做 / 产出）

### 第 0 步：规则与数据边界确认（0.5 天）

- **已完成**：官网赛程、资格、赛题产出、初赛/决赛交付物、数据合规规则；本地 8 表、关联关系和 29 条缺失图片路径复核。
- **项目决策（不是官方明文许可）**：官网未明确禁止的外部闭源/商业模型 API、联网检索、第三方托管和线上部署按允许推进，答疑不再作为开发前置。
- **持续观察但不阻塞开发**：图片下载包、PPT/视频规格、评分权重和路演时长；若后续官方公告与项目假设冲突，以官方公告为准。
- **继续执行的硬边界**：比赛数据仅限比赛使用、隐私安全、知识产权、原创性和比赛结束后的数据处置要求；外部服务须记录服务商、模型版本、发送字段、成本和降级，密钥不得入库。
- **产出**：[比赛约束清单](competition-constraints.md) 已写入，并在 README 顶部建立统一入口。

### 第 1 步：数据画像与关联校验（1–1.5 天）

> **状态：已完成（2026-09-01）**。稳定报告见 [数据画像与关联校验](data-profile.md)，逐表字段见 [字段字典索引](field-dictionaries/README.md)，机器可读审计快照见 `artifacts/data-profile-20260901/profile.json`。

- **做什么**：读入 8 张表，产出数据画像报告，验证 README 的数字（138 会话 / 998 消息 / 80 工单）与关联关系。
- **怎么做**：写只读脚本 `scripts/profile_data.py`，重点算——
  - 所有 ID（订单号、物流单号、message_id、工单号）**按字符串读**，验证无浮点化；
  - `scene_major/scene_minor` 分布 + 交叉表（哪些二级场景样本极少，直接影响 Macro-F1）；
  - 会话 → 订单 → 工单的关联完整率（复核 README 的「113/113、80/80」）；
  - 每类工单关键字段可用率（如不良反应「是否就医」非空比例）；
  - `image_path` 有值但文件缺失的比例，写进数据边界。
- **产出**：`docs/data-profile.md` + 每表字段字典。**后面所有判断的地基。** 当前结论为“足以进入评测立标，但不足以直接声称情绪/风险模型有效”。

### 第 2 步：把「评测集」和标注口径立起来（1.5–2 天）——**最关键的一步**

决定项目是「有据可查」还是「自说自话」。

- **场景识别**：用 `scene_major/scene_minor` 做金标签。**按会话 / 买家分组切分**（不能按消息随机切）。指标：一级 / 二级 Macro-F1 + 混淆矩阵。
- **情绪**：无金标签 → 定小而清晰的标签体系（如 平静 / 不满 / 焦虑 / 愤怒 4 档），**人工标注 60–100 条会话**作为评测集，规则写文档。不追求全量。
- **风险等级 P0–P3**：**用工单字段反推弱标签**当参考真值——如「不良反应工单 且 是否就医=是」→ P0；「售后退货 且 是否异常=是」→ P1。形成《风险规则映射表》。
- **产出**：`evaluation/cases/`（固定评测会话集）+ `evaluation/rubrics/`（情绪 / 风险 / 回复三套评分标准）。这套东西在 PPT §7 直接就是「评测结果」。

### 第 3 步：规则风险引擎设计（1 天，可与第 2 步并行）

- **做什么**：把「确定性规则兜底」做成可运行的规则集。
- **怎么做**：从 §2 映射表出发，定义安全关键词（就医、红肿、刺痛、过敏…）+ 状态规则（工单未闭环、异常退货），明确「模型不允许下调规则触发的高风险」。
- **产出**：`backend/app/risk/rules.py` + 规则清单文档，每条规则能指到触发它的原始消息 / 字段。

### 第 4 步：LLM 结构化输出的可行性验证（1–1.5 天）

- **做什么**：验证「聊天文本 → README §11 那个 JSON」链路能否稳定跑通。
- **怎么做**：先不搭完整 Agent，写最小脚本，拿 10 条真实会话喂 LLM，强制结构化输出（scene / intent / emotion / risk_level / evidence_message_ids / reply 三段式）。重点验证：
  - JSON 是否稳定可解析；
  - `evidence_message_ids` 是否真能指回原文（防幻觉）；
  - 事实字段是否只来自工具查询结果、缺数据时是否老实写「暂未查询到」。
- **产出**：`docs/llm-io-contract.md`（提示词版本 + JSON schema + 失败案例）+ 场景识别的离线 F1 基线。

### 第 5 步：选定两个黄金演示案例（0.5 天）

- **做什么**：从真实数据锁定场景 A（不良反应升级）和场景 B（物流 / 换货闭环）各一条会话。
- **怎么做**：优先挑关联链条完整、字段齐全的——如不良反应表 `S00082`（有症状描述、批次号、就医字段），物流表 `S00011`（破损、原地址补发）。
- **产出**：`evaluation/cases/golden_A.json`、`golden_B.json`，后续所有功能都用这两条回归。

### 第 6 步：进入 README 的工程开发（阶段 1–5）

前 5 步产出（数据画像、评测集、规则集、IO 契约、黄金案例）齐了，就按 README 开发路线做：数据层 + 静态界面 → 第一个端到端闭环 → 第二个场景 → 评测加固 → 提交路演。**每完成一个功能，用黄金案例回归。**

## 3. 时间与优先级

| 阶段 | 天数 | 是否可并行 |
| --- | ---: | --- |
| 第 0 步 规则确认 | 0.5 | 独立 |
| 第 1 步 数据画像 | 1–1.5 | 独立，最先做 |
| 第 2 步 评测立标 | 1.5–2 | **最高优先级** |
| 第 3 步 规则引擎 | 1 | 与第 2 步并行 |
| 第 4 步 LLM 验证 | 1–1.5 | 依赖第 1 步 |
| 第 5 步 黄金案例 | 0.5 | 依赖第 1 步 |

调研 / 立标阶段合计约 **5–6 天**，之后进入 README 的开发路线。

**一句话原则**：先证明「场景能分、风险能判、依据能回溯、回复不编造」四件事在真实数据上成立（第 1–4 步），再动 UI 和 Agent 编排。对应 README §19「范围停止规则」。
